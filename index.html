Since April 2026, I have worked on the data behind an Amazon brand agency's platform: sales and traffic reports, advertising data, inventory, reimbursements and AI-generated product content. It runs as five apps on one shared Postgres database. I didn't build these apps. From May, I was the only person on the team fixing their bugs, full time: I found out why their numbers or features went wrong, submitted each fix to my manager for review, and shipped it once approved.

What I found most often

Selected analyses

Log analysis · all five apps

Outages that hit every app at once

Problem
All five apps sometimes refused every request for a few seconds to five minutes, with "503 Service Unavailable" and no clear trigger.
Analysis
I pulled 12 days of request logs, grouped the refused requests by minute, and lined each burst up against the database API's own log.
Finding
37 outages and 1,848 refused requests, 15 of the outages on a single day. Every outage minute had one failed schema reload, cut off by an 8-second limit. The slowest reload took 13.3 seconds.
Outcome
Raised that one limit to 300 seconds. Live since Nov 5. Limits on user requests stayed the same.

AI evaluation · content review

Testing an AI reviewer on all its past answers

Problem
An AI step that reviews generated product copy failed text while its own note said the text "actually complies".
Analysis
A re-run rule caught these contradictions only when the note used one of a fixed list of phrases. I measured that rule against every saved review since it started. Keyword counts swung from about 125 to 1,800 depending on the pattern, so I didn't rely on them.
Finding
927 saved fails said in their own note that the text passed. 630 of them were never re-run, because the phrase list missed their wording.
Outcome
Replaced the phrase list with a short AI check that reads what each failing note concludes. Tested on all 2,741 labelled review notes with the labels hidden, then verified live.

Data reconciliation · report uploads

Ad data filed under the wrong account

Problem
Advertising bulk files for one seller account appeared under another, mixing their ad data.
Analysis
I compared the account named in each of the 279 past file names with the account it was filed under. Then I matched every suspect row against its correct account on four keys.
Finding
5 imports contradicted their file names. Four of them had put 120,238 rows under the wrong account, and every one of those rows already existed under the right one.
Outcome
Misfiled rows backed up, with zero data loss. A file-name check now blocks wrong uploads. Run on the history, it passed all 274 correct ones and caught the 5 wrong ones.

Data completeness · all five apps

Lists that silently stopped at 1,000 rows

Problem
Lists and totals came back incomplete with no error: groups missing members, report rows gone, claims missing from search.
Analysis
I swept the database reads in all five apps for any that could return more than 1,000 rows. In the largest app, that meant 158 server functions and 297 database function calls.
Finding
The database API returns at most 1,000 rows per request, and the code treated that as the whole list. Reads without a fixed sort order also overlapped between pages: in one claims list, about 1 in 5 items never appeared.
Outcome
Live in all five apps since Oct 21. One shared reader returns every row or raises an error, and a CI check blocks new reads that skip it.

Segmentation · multi-country sellers

Numbers from the wrong country

Problem
For brands selling in the US, Canada and Mexico, some pages counted other countries' figures as US numbers.
Analysis
Before changing anything, I measured on live data which pages actually showed wrong numbers. After the change, I compared each report's output old against new, in both directions.
Finding
The wrong pages read by account and ignored the marketplace. Some stock views quietly defaulted to the US.
Outcome
Affected pages in all five apps follow the marketplace picker. US-only reports now say so, and every other report kept exactly the same numbers.

Data collection · GitHub change audit

A weekly count of fixes that was quietly wrong

Problem
Every Monday the team needed a count of the fixes made to its server functions across all the codebases, recorded in a tracking table and reported onward.
Analysis
Each week I pulled every merged pull request from GitHub, read its code changes, and recorded each verified fix with the tables and apps it touched. When the numbers looked off, I checked how they were collected.
Finding
Two measurement errors. The audit covered four codebases when there were five, so every earlier week was undercounted. Sorting pull requests by their titles also missed real fixes, 5 in one week, because most of them mixed features and fixes.
Outcome
Fixed the scope and re-swept the earlier weeks, which recovered 4 missed fixes. Classification now reads each change, not its title. Commit authors didn't show who drove a change, so I tested another signal: it matched 6 of 6 known cases and 0 of 18 others.

SQL · reconciliation

Prove nothing is lost before removing data

Before any misfiled ad row was removed, every one had to exist under its correct account, matched on all four keys.

select count(*) as misfiled,
       count(c.entity_id) as found,
       count(*) - count(c.entity_id) as lost
from misfiled_rows m
left join ad_entities c
  on  c.seller_id = m.correct_seller_id
  and c.marketplace_id = m.marketplace_id
  and c.entity_type = m.entity_type
  and c.entity_id = m.entity_id;
-- 120,238 misfiled, 120,238 found, 0 lost

SQL · log analysis and fix

Find the outages, then fix the setting

Refused requests grouped by minute showed each outage as a burst. Each burst matched one failed schema reload.

Analysis

select
  date_trunc('minute', created_at) as minute,
  count(*) as refused
from request_log
where status = 503
  and path like '/rest/v1/%'
group by 1
order by 1;

Fix

-- Give the schema reload room.
-- User requests keep their own limits.
alter role authenticator
  set statement_timeout = '300s';
notify pgrst, 'reload config';

TypeScript · data completeness

Read every row, or fail loudly

A plain read returns at most 1,000 rows and no error. The fix pages through in a fixed order and stops with an error instead of returning part of a list.

Before

// Returns at most 1,000 rows.
// Nothing says the list was cut.
const { data } = await supabase
  .from("orders").select("*");

After

async function fetchAll(table: string) {
  const size = 1000, rows: unknown[] = [];
  for (let from = 0; ; from += size) {
    const { data, error } = await supabase
      .from(table)
      .select("*")
      .order("id") // fixed order: no overlap
      .range(from, from + size - 1);
    if (error) throw error; // fail loudly
    rows.push(...data);
    if (data.length < size) return rows;
  }
}

More investigations

Not every investigation ended in my own pull request. In these, the lead developer shipped the fix, no code change was needed, or the fix was waiting for approval at hand-over.

  • 1,654 failed runs in a rowAn automated pipeline that groups products created nothing for three weeks. Two queued products were still filed under a former brand, and one refusal cancelled each whole run. The fix shipped and I verified it live.
  • Uploads reported as missingA reconciliation sheet listed fee reports as never uploaded. I matched each gap to its cause: some imports failed without a log entry but another upload covered the same month, and the rest were older than the data available to download. No data was lost.
  • Wrong-size AI recommendationsAn AI recommender showed wrong-size products as confident top substitutes. I found three separate causes: a candidate cap, the ranking, and an auto-approve check. The fix also clears 1,620 stale scores.
  • A page that failed every loadA setup step failed all 162 loads in 9 days. The page packed every template ID into the request URL, which grew to about 24,600 characters until the server refused it.
  • Approved copy clients never sawApproving an older version of a product title never made it the current one, and the client portal shows only current versions. I traced 33 affected versions and designed a repair with a backup.

How I work

  1. 1Start from the number that looks wrongI open the user's own record and reproduce exactly what they saw.
  2. 2Prove it with dataQuery results, request logs and row counts. If a cause can't explain every detail in the report, I keep looking.
  3. 3Measure the reachI count every record, page and report the same cause touches before deciding on the fix.
  4. 4Compare before and afterI check old against new output in both directions before calling a change safe.
  5. 5Test on all the dataAn AI change gets tested on every saved output, not only the example in the ticket.
  6. 6Ship it as a reviewed pull requestEach fix goes on its own branch with its spec update and deploy steps, passes the tests against the latest code, and is reviewed before merge. After merge, I run the deploy steps and check the result live.
  7. 7Write it upRoot-cause reports, daily status reports and a weekly report to my manager. At my manager's request, I shared my reporting routine with two teammates.
